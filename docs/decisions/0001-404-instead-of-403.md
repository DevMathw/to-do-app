# 0001 — 404 instead of 403 for tasks you do not own

**Status:** accepted · 2026-09

## Context

When a user requests `/api/v1/tasks/42` and task 42 belongs to someone else,
the API has to choose between two honest answers:

- `403 Forbidden` — "this exists, but it is not yours"
- `404 Not Found` — "there is nothing here for you"

The first version of this project returned `403`. It reads as the more precise
answer, and it is what most tutorials do.

## Decision

Return **404** for both "does not exist" and "exists but belongs to another
user". The ownership filter is applied in the query itself
(`WHERE id = ? AND owner_id = ?`) rather than fetched-then-checked, so the two
cases are indistinguishable by construction.

## Rationale

A `403` confirms that the id exists. Walking `/tasks/1`, `/tasks/2`, `/tasks/3`
and recording which return 403 versus 404 reveals how many tasks the system
holds and which ids are live — a resource-enumeration side channel that costs
an attacker nothing.

Doing the check inside the `WHERE` clause also removes a whole class of bug:
there is no window in which the code holds another user's row in memory and
relies on a later `if` to avoid leaking it.

## Consequences

- Slightly less helpful during debugging: a developer hitting the wrong id gets
  a `404` and no hint that the row exists.
- The `403` branch, and the tests covering it, are gone.
- `tests/test_authorization.py` asserts `404` explicitly for every route, so the
  decision cannot be reverted by accident.
